# SRC 报告写法（版式下限）

> **版式只认 `~/.grok/rules/vuln-report-format.md`。本文件是它不存在时的下限。**
> 本机实测（2026-09）：`/mnt/c/Users/<USER>\.grok\rules` **不存在** —— 所以现在按本文件写。哪天该 rules 出现了，以 rules 为准，本文件作废。
> **定级不认本库。** 本文件只管「一份报告里必须有什么」，不管「这个洞值多少分」。
> 收不收只认 `漏洞不收清单.md`。

---

## 一、结构（缺一段就是没写完）

| 段 | 写什么 |
|---|---|
| **漏洞名称** | `xx公司xx网站存在xx漏洞`。公司名要对得上**备案主体**，不写品牌简称 |
| **危害描述** | 按实际影响写，可以适度展开推演（经验上限 **+20~30%**）。**事实部分一个字不许吹** —— 吹过头会被审核按不实驳回 |
| **漏洞 URL** | 存在漏洞的那个**接口**。小程序 = `协议 + host + api 路径`（抓包看到的那个） |
| **漏洞描述** | 先给**资产证明**（见 §二），再写路径：访问 `https://www.xxx.com/admin`（或小程序/App）→ 进入某功能 → 抓包 → 发现某参数存在某漏洞 |
| **漏洞详情** | 数据包**截图** + 截图后面**贴数据包原文**（这就是提交时的 PoC） |
| **修复建议** | 简单写，点到即可 |

## 二、资产证明（最容易被打回的一项）

**必须先证明这个资产属于你测的那家主体**，否则审核不认：

- **ICP 备案**截图 / 备案号 —— 证明域名归属该公司
- **小程序 / App** —— 同主体的备案信息，或开发者主体
- **子公司 / 边缘资产** —— 用企查查 / 爱企查的股权链把归属串起来
- **云上的服务器 —— 交实际运营的公司**，不是云厂商

## 三、纪律

- **敏感值打码**：手机号、身份证、Cookie / Token、真实口令**不进报告正文、不落盘**（`漏洞不收清单.md` 同一条）
- **只写证实过的**：请求 + 回包 + 差分。不写「疑似」「可能存在」「可推断」
- **假点不写**：`漏洞不收清单.md` 上的类别一律不写
- **一条报告一个洞**：不要把三个差分写成一个洞，也不要一条里塞多个接口
- 越权报告要写清**绕过的是哪一层**（前端守卫 / 网关 / 对象 id），别混

## 四、提交平台（经验，非硬规则）

| 情况 | 去哪 |
|---|---|
| 权重 > 1 的公益 / 通用目标 | 补天 |
| 权重 0 的 | 漏洞盒子 |
| edu 目标 | 360 收 edu；**公益类一般不收港澳台** |
| 自建 / 授权 SRC | 按用户指定平台 |

权重怎么查：站长之家一类平台。**这条只是经验，平台规则会变，以平台当前公示为准。**
